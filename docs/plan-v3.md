# ObsidianWinSync リリース完成計画

## 1. 現在地

現時点で以下は実装済み。

- ローカル Vault と iCloud Vault の双方向同期
- 追加、更新、削除、競合の判定
- dry-run、定期同期、二重起動防止
- 上書き・削除前バックアップと復元 CLI
- 同期ログと状態ファイルの前世代保存
- タスクトレイ常駐、設定画面、一時停止、通知、自動起動
- `obsidian-win-sync.json` の標準配置と探索
- Windows 用アイコンと自己完結型 win-x64 EXE
- 自動テスト29件

次の目標は、新機能を広げることではなく、競合処理と障害耐性を完成させ、第三者へ安全に配布できる最初の正式版を作ることとする。

## 2. 正式版の完了条件

- 定期同期中に競合ダイアログが突然連続表示されない
- 競合を一覧で確認し、差分を見て個別または一括解決できる
- 状態ファイルを別の Vault 組み合わせへ誤適用しない
- 状態ファイル破損、ファイルロック、ディスク不足、同期中断から安全に復帰できる
- 24時間以上の常駐試験で多重同期、ハンドルリーク、通知連打が発生しない
- .NET 未導入の Windows でインストール、初期設定、自動起動、更新、アンインストールができる
- README の手順だけで非開発者が利用を開始できる

## 3. 優先順位

### P0: リリース前に必須

- 状態ファイルと Vault の関連付け
- 競合一覧・差分・保留処理
- エラー時のログと復旧性
- 長時間常駐試験
- 配布物と初回利用手順

### P1: 正式版に含めたい

- 最後の同期結果と履歴表示
- 通知の重複抑制
- バックアップを GUI から復元
- 自動起動設定の回帰試験

### P2: 正式版後

- 三方向自動マージ
- 複数 Vault
- FileSystemWatcher による低遅延化
- 自動アップデート

## 4. Phase 1: 状態管理と障害耐性

### 実装内容

- 状態ファイルへ local / iCloud Vault の正規化済みパスと識別子を保存する
- 設定された Vault が状態ファイルと一致しない場合は同期を停止する
- 状態スキーマをバージョン2へ上げ、バージョン1からの移行処理を追加する
- `state.json` が破損している場合は `state.json.bak` を検査し、利用者の確認後に復元可能にする
- 同期開始、成功、競合、キャンセル、失敗をすべてログへ記録する
- 一時的な I/O エラーと継続不能なエラーを分類する
- スキャン中に一部ファイルを読めなかった場合、欠落を削除と誤判定しないよう同期全体を停止する

### 受け入れ条件

- 別の Vault を設定しても以前の削除履歴が適用されない
- 壊れた状態ファイルで自動同期が開始されない
- ロックされたファイルを削除済みとして扱わない
- 失敗理由と対象相対パスをログから確認できる

## 5. Phase 2: 競合センター

### 設計方針

定期同期では競合を保留リストへ追加し、同期可能な他ファイルだけを処理する。モーダルダイアログは自動同期中に表示しない。

タスクトレイの「競合を確認」から専用画面を開く。

### 画面機能

- 競合ファイルの相対パス、更新日時、サイズ、競合種別を一覧表示
- テキストファイルは local / iCloud の行単位差分を表示
- バイナリはサイズ、更新日時、ハッシュを表示
- local を採用、iCloud を採用、保留を選択
- 複数項目を選択して同じ側を一括採用
- 解決前に両側の現在状態を再検査し、さらに変更されていれば再確認
- 解決時も上書き・削除前バックアップを作成

### 受け入れ条件

- 10件以上の競合があってもダイアログが連続表示されない
- 競合解決中にファイルが変化しても古い内容で上書きしない
- アプリ再起動後も未解決競合を再検出できる
- Markdown、日本語、UTF-8、改行コード差を読める形で表示できる

## 6. Phase 3: 常駐アプリの仕上げ

### 実装内容

- 最終同期時刻、次回同期時刻、コピー・削除・競合件数を表示する状態画面
- 直近の同期履歴を表示する画面
- バックアップ一覧と復元操作を GUI へ追加する
- 同じエラー通知を一定時間まとめ、通知の連打を防ぐ
- 一時停止状態をアプリ再起動後も保持するかを設定可能にする
- 設定保存後に Vault または状態ファイルの不整合を検証する
- 初回起動時に設定画面を自動表示する
- 設定ファイルが見つからないエラー通知から設定画面を直接開けるようにする

### 受け入れ条件

- JSON を直接編集しなくても初期設定、同期、競合解決、復元ができる
- 同期間隔変更がアプリ再起動なしで反映される
- 連続失敗しても通知は設定した間隔以上に表示されない
- タスクトレイメニューから現在状態を判断できる

## 7. Phase 4: テスト拡充

### 自動テスト

- CLI の終了コードと標準出力を検証するエンドツーエンドテスト
- 状態スキーマ移行と Vault 不一致テスト
- 競合保留、再検査、一括解決テスト
- バックアップ容量上限と保持期間テスト
- ログローテーションとエラーログテスト
- 設定探索順と初回保存先テスト
- 日本語、絵文字、長いパス、大容量ファイルの統合テスト
- キャンセル、ロック、部分コピー、ディスク不足を模した障害注入テスト

### 実機試験

- Obsidian を起動したまま local と iCloud の両側を編集する
- iCloud ファイルをオンラインのみ、ダウンロード中、ロック中の状態で試す
- スリープ、休止、ネットワーク切断、復帰を繰り返す
- Windows ログイン時の自動起動と二重起動を確認する
- 24時間以上常駐させ、メモリ、ハンドル数、ログ容量を記録する

### 受け入れ条件

- 自動テストがすべて成功する
- 24時間試験で同期処理の重複がない
- メモリとハンドル数が継続的に増加しない
- 障害後の再同期で両 Vault の整合性を回復できる

## 8. Phase 5: 配布と運用

### 実装内容

- アプリバージョン、製品名、会社名、著作権情報を EXE に埋め込む
- 配布フォルダに EXE、設定サンプル、README、ライセンスを含める
- PDB を通常配布物から除外し、必要ならデバッグ用アーカイブへ分離する
- ZIP 配布またはインストーラーを作成する
- インストーラー採用時はユーザー単位インストールを基本とする
- 更新時に設定、状態、バックアップを保持する
- SHA-256 チェックサムを公開する
- コード署名の有無と SmartScreen の影響を文書化する
- アンインストール時にユーザーデータを残すか選択できるようにする

### 受け入れ条件

- .NET SDK 未導入のクリーンな Windows で起動できる
- 更新後も設定と同期状態が維持される
- アンインストール後に自動起動登録が残らない
- 配布物のチェックサムを検証できる

## 9. Phase 6: ドキュメントと正式リリース

### 必要な文書

- 5分で終わる初期設定手順
- iCloud Vault パスの確認方法
- 初回同期で必ず dry-run 相当の内容を確認する手順
- 競合解決とバックアップ復元手順
- ログ収集と障害報告手順
- 設定・状態・バックアップの保存場所
- 既知の制限
- バージョンアップとアンインストール手順

### 正式リリース判定

以下をすべて満たした場合のみ正式版とする。

- P0 項目がすべて完了
- 自動テスト、実機試験、24時間常駐試験が成功
- 重大または高優先度の既知不具合がない
- 新規 Windows ユーザーが README のみで導入できる
- バックアップからの復元を実機で確認済み
