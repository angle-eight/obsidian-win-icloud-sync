# ObsidianWinSync 実装計画

## 1. 目標

Windows 上のローカル Vault と iCloud Drive 上の Obsidian Vault を双方向同期する。
最初のリリースはコンソールアプリとし、安全に手動実行できることを優先する。

MVP の完了条件は次のとおり。

- JSON でローカル側と iCloud 側の Vault パス、および同期間隔を秒単位で設定できる
- 前回の正常同期時点を基準に、作成・更新・削除を双方向へ反映できる
- 両側で同じファイルが変更された場合は自動上書きせず、差分を表示して選択できる
- 中断やコピー失敗が起きても、前回の正常な同期状態を失わない
- dry-run で実際の変更前に同期内容を確認できる
- 同期ロジックが自動テストされている

## 2. MVP の対象範囲

### 含めるもの

- 1 組の Vault の同期
- ファイルの追加、更新、削除
- テキストファイルの行単位差分表示
- 競合時の `local` / `icloud` / `skip` 選択
- 手動同期と一定間隔での繰り返し実行
- 除外パターン、ログ、dry-run

### MVP では含めないもの

- ファイル内容の自動マージ
- 複数 Vault の管理
- GUI、タスクトレイ、Windows 起動時の自動起動
- iCloud API との直接通信
- 履歴バックアップや端末間の同期サーバー

これらはコンソール版の安定後に検討する。

## 3. 設計方針

### 構成

責務を次の単位に分ける。

- `Configuration`: JSON の読み込み、検証、既定値
- `FileScanner`: Vault を走査し、相対パスごとの状態を取得
- `SyncStateStore`: 前回の正常同期スナップショットを保存
- `SyncPlanner`: 前回状態と両側の現在状態から操作計画を作成
- `SyncExecutor`: コピー、削除、ディレクトリ作成を安全に実行
- `ConflictResolver`: 差分表示と利用者の選択
- `ConsoleUi`: コマンド、進捗、結果の表示

同期判定とファイル操作を分離し、同期判定は実ファイルシステムなしでもテストできるようにする。

### ファイル識別と変更判定

ファイルは Vault からの相対パスで識別する。各スナップショットには最低限、存在有無、サイズ、最終更新時刻、内容ハッシュを保持する。

更新時刻とサイズを高速な事前判定に使い、必要な場合にハッシュで内容を確定する。時刻だけには依存しない。

### 同期ルール

各相対パスについて、前回の正常同期状態と現在の local / iCloud を比較する。

| local の変化 | iCloud の変化 | 処理 |
|---|---|---|
| なし | なし | 何もしない |
| あり | なし | local を iCloud へ反映 |
| なし | あり | iCloud を local へ反映 |
| あり | あり、内容は同一 | 同期済みとして状態だけ更新 |
| あり | あり、内容が異なる | 競合として利用者に確認 |

削除も変更の一種として扱う。前回は両側に存在し、一方だけが削除され、他方が未変更なら削除を伝播する。削除と編集が同時に起きた場合は競合とする。初回同期で一方にしか存在しないファイルは削除扱いにせず、存在する側からコピーする。

### 安全性

- 実行前に両パスが存在し、同一パスでも包含関係でもないことを検証する
- Vault 外へ解決されるパスや reparse point / symlink は既定で処理しない
- コピーは同一ディレクトリの一時ファイルへ書き、完了後に置換する
- 同期状態は全操作成功後に一時ファイルから原子的に更新する
- 同期中はロックファイルで二重起動を防ぐ
- dry-run ではファイルと同期状態を一切変更しない
- iCloud ファイルが未ダウンロード、ロック中、または一時的に利用不能な場合を想定し、限定回数の再試行後に失敗として報告する

## 4. 設定ファイル案

```json
{
  "localVaultPath": "C:\\Users\\user\\Documents\\ObsidianVault",
  "icloudVaultPath": "C:\\Users\\user\\iCloudDrive\\iCloud~md~obsidian\\Documents\\Vault",
  "intervalSeconds": 30,
  "excludePatterns": [
    ".obsidian/workspace*.json",
    ".trash/**",
    "*.tmp"
  ],
  "stateFilePath": "state.json"
}
```

`intervalSeconds` は同期間隔を秒単位で指定する。省略時のデフォルト値は `30` 秒とし、0 以下などの不正値は設定エラーとして扱う。

実際の iCloud パスは環境ごとに異なるため固定値にせず、設定検証コマンドで存在と読み書き可否を確認する。

## 5. 実装フェーズ

### Phase 0: プロジェクト基盤

- ソリューションを作り、アプリ本体と xUnit テストプロジェクトを分離する
- `bin/`, `obj/`, 状態ファイル、ログ、一時ファイルを `.gitignore` に追加する
- 設定、ログ、終了コードの基本方針を決める
- CI で build と test を実行する

完了条件: クリーン環境で restore、build、test が成功する。

### Phase 1: 設定と読み取り専用スキャン

- 設定モデル、JSON 読み込み、入力検証を実装する。同期間隔は秒単位で受け取り、省略時は 30 秒とする
- `validate` コマンドで両 Vault の問題を表示する
- 除外パターンを適用してファイル一覧と fingerprint を作る
- `scan` コマンドで検出結果を表示する

完了条件: 不正パス、同一/包含パス、除外対象、空 Vault、Unicode 名に加え、同期間隔の省略時既定値と不正値をテストできる。

### Phase 2: 同期計画エンジン

- スナップショットの形式とバージョンを定義する
- 追加、更新、削除、同一変更、競合を判定する純粋なロジックを実装する
- `sync --dry-run` で操作計画だけを表示する

完了条件: 同期ルール表の全組み合わせと初回同期を単体テストで網羅する。

### Phase 3: 安全な同期実行

- ディレクトリ作成、原子的コピー、削除、再試行を実装する
- 二重起動防止と構造化ログを追加する
- 全操作成功後だけ同期スナップショットを更新する
- 途中失敗から次回安全に再実行できることを確認する

完了条件: 一時ディレクトリを使った統合テストで双方向同期、削除、ロック、途中失敗、再実行が成功する。

### Phase 4: 競合解決

- テキストファイルには unified diff、バイナリにはメタ情報を表示する
- `local` / `icloud` / `skip` を選択可能にする
- 非対話実行時は競合を未解決のまま残し、非 0 の終了コードを返す
- 選択結果を実行前サマリーとログに残す

完了条件: 編集対編集、編集対削除、バイナリ競合を上書き事故なく処理できる。

### Phase 5: 定期実行

- `watch` コマンドで設定間隔ごとに同期する
- 前回の処理が終わる前に次の同期を開始しない
- Ctrl+C で現在の安全な境界まで処理し、正常終了する
- 連続失敗時のログ肥大化と過剰な再試行を防ぐ

完了条件: 長時間テストで多重実行せず、停止と再開後も整合性が保たれる。

### Phase 6: リリース準備

- self-contained 単一ファイル配布を検証する
- 初期設定、iCloud 側フォルダの確認、dry-run、復旧手順を README に記載する
- Windows で実 Vault に似せた受け入れ試験を行う
- 既知の制限とログ収集方法を記載する

完了条件: 新しい Windows 環境で README だけを見て設定と初回同期ができる。

## 6. テスト戦略

- 単体テスト: 変更判定、競合判定、除外、設定検証、パス正規化
- 統合テスト: 一時ディレクトリ間のコピー、削除、状態保存、障害後の再実行
- 手動試験: 実際の iCloud Drive の遅延、未ダウンロードファイル、Obsidian 起動中の更新
- 回帰ケース: 日本語名、絵文字、長いパス、大文字小文字差、空ファイル、大容量ファイル、同一時刻で内容が違うファイル

実時刻への依存を避けるため、時計とファイルシステム操作は差し替え可能にする。テストでは十分に小さい一時 Vault を使用する。

## 7. 推奨タスク順序

1. T-1: solution、xUnit、`.gitignore`、CI
2. T-2: 設定モデルと `validate`
3. T-3: ファイル走査、除外、fingerprint
4. T-4: 同期状態モデルと永続化
5. T-5: 同期計画エンジンと網羅テスト
6. T-6: `sync --dry-run`
7. T-7: 原子的コピーと双方向の追加・更新
8. T-8: 削除伝播と障害時の再開
9. T-9: 競合差分と対話解決
10. T-10: ロック、ログ、終了コード
11. T-11: `watch` と graceful shutdown
12. T-12: 配布、README、Windows 受け入れ試験

各タスクは小さな失敗テストから始め、1 タスク 1 コミットとする。

## 8. MVP 後の候補

- 三方向マージと競合コピーの自動作成
- 複数 Vault
- Windows タスクトレイ UI と通知
- Windows 起動時の自動開始
- 同期履歴、バックアップ、ロールバック
- ファイル監視による即時同期（定期フルスキャンは整合性確認として残す）
